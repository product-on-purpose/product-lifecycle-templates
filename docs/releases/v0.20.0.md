# product-lifecycle-templates v0.20.0

Release date: 2026-10-21. This project follows [Semantic Versioning](https://semver.org/).

## Summary

**The library grows from 47 bundles to 49 with a test strategy and a positioning statement.** A test
strategy sets the testing approach that every project inside one organization or program starts from, so
each project's test plan only has to say where it differs. A positioning statement records how a product
stands against a named alternative, for a specific target customer, now, so the vision, the roadmap and the
messaging built on top of it share one stance.

Neither new bundle is proven to help anyone. Both are researched, and each says where its sources disagree.

## New

- **[`test-strategy`](../../templates/test-strategy/)** - the standing document that sets the default
  testing approach for every project inside one organization or program: which levels, types, tools and
  environments apply, how testing is governed, and the rule by which each project's test plan either
  follows the default or states a reasoned deviation. It ships in one size, lean, with seven sections,
  ending in a Review Trigger that names what reopens it. A row marked Mandatory must name the law,
  regulation, contract or past incident that makes it so. It is the seventh `standing-standards` member,
  at `classification: foundation`.
- **[`positioning-statement`](../../templates/positioning-statement/)** - the internal, present-tense
  record of how this product stands against a named alternative, for a specific target customer, now. It
  is not the vision, which looks forward; not messaging, which is built on top of it once it is settled;
  and not a battlecard or a positioning map. It ships in one size, lean, with five sections: Purpose and
  Boundary, The Statement, The Components, Why This Positioning, and When We Revisit It. Its guide names
  both camps in the dispute over who owns the statement, product management or product marketing. It is
  the sixth `strategy-docs` member and sits third in that family's chain, after the vision and the
  strategy.

## Improved

- **Both agent skills now name the two new document types.** An agent decides whether to load a skill
  from its description, so a request to write or grade a test strategy or a positioning statement now
  reaches the skill that fills or grades it.
- **Three existing bundles now link to the new ones.** The test plan routes a reader who needs the
  organization-wide default to the test strategy. The North Star metrics bundle notes that it now sits
  fourth in the strategy chain, after the positioning statement. The product vision bundle links to the
  positioning statement where it describes the line between the two.
- **Every quotation in both research logs was checked against the source's raw text**: 291 quotations
  from 43 sources for the test strategy, and 297 quotations from 59 sources for the positioning statement.
- **The choosing-a-template guide names both new bundles.** The positioning statement appears under
  defining what to build, and the quality section points to the test strategy.
- **The `define` phase now has a written boundary.** A `define` document converges on one chosen problem
  and may name the concept chosen for design, but it never specifies the solution. The problem statement
  is still the only `define` bundle; a design brief and an opportunity statement are the next candidates.

## Fixed

- **The fill skill, the grading skill and `AGENTS.md` now give the library's current size.** Two
  sentences still said 48 bundles, one said only the Tier-1 floor was built, and one said a phase-only
  search reaches "28 of the 48". Each now matches the 49 bundles the library ships.
- **Build-cost reports now count the whole build.** The report generator missed agents that a build
  runs outside its workflows, which was about 40 percent of each of this release's two builds. One earlier
  report, the problem statement's, rose by about 5 percent for the same reason.

## Known issues

- **Nothing here makes any bundle better.** All 49 are `beta`, and no page calls one proven.
- **The test strategy's program scope rests on published program strategies, not on a standard's
  wording.** ISTQB's official glossary defines a test strategy "within an organization". The library's
  "organization or program" scope is the maintainer's ruling, supported by the published program
  strategies the build read, among them Ofgem's and DCC's. ISO/IEC/IEEE 29119-3's own text was not reached, so whether that standard renamed the
  artifact remains open.
- **Who owns a positioning statement is contested.** The sources split between product marketing and
  product management. The guide offers a default, product management owns it and product marketing drafts
  it, as the library's reasoning, not as a finding.
- **A search filtered to one axis value can be cut short.** The MCP server's `search_templates` returns at
  most 8 candidates, and `deliver` and `utility` hold 10 bundles each and `develop` 9. `total_matched` in
  the response tells you when a list was cut.
- **Build cost is measured, not a rate.** At API list rates, the whole build cost $35.11 across 18 agents
  for the test strategy, and $30.25 across 18 agents for the positioning statement
  ([`bundle-builds/`](../../bundle-builds/INDEX.md)). Both are above the usual range because each ran an
  Opus head writer and a fix agent outside its workflows.
