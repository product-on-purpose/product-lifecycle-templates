# product-lifecycle-templates v0.13.0

Release date: 2026-09-23. This project follows [Semantic Versioning](https://semver.org/).

## Summary

**The library grows from 31 bundles to 33 with two new templates: an issue log and a definition of
ready.** The issue log is the record of problems that have already happened on a project and who is
fixing each one. The definition of ready is a team's agreement on when a backlog item is ready to start.

Neither is proven to help anyone; both are researched, and both say where their sources disagree. The
definition of ready goes further: several of its own sources argue a team may be better off without one,
and the bundle treats keeping none as a legitimate outcome.

## New

- **[`issue-log`](../../templates/issue-log/)** - one owner per issue, an escalation rule decided before
  it is needed, and closure confirmed by someone other than the person who did the fix. Lean for a team
  logging its own issues; full adds the closure record and links to the risk, change request and decision
  behind each issue. **The template asks you to state what counts as an issue first**, because the named
  standards (PMI, APM and two editions of PRINCE2) define one four different ways.
- **[`definition-of-ready`](../../templates/definition-of-ready/)** - a team's agreement on when a
  backlog item is ready to pull into a sprint. Five short sections: why the team keeps one and when it
  would stop, the criteria written as questions, the one kind of hard stop its sources allow (a dependency
  on another team or vendor), a way in for a top-priority item that misses, and a trigger for revising it
  when it lets too much through or blocks too much. **One size only, on purpose**: no source read argues
  for a bigger one, and the ones that address its size argue for a smaller one.

## Improved

- **Every quotation in both bundles' research logs was checked against the source's raw text**, not a
  retrieval tool's summary. The check caught a research agent reporting that the European Commission's
  project methodology had no escalation field in its issue log. It has one.
- **The template chooser, the agent guide, the contributing guide and two family contracts no longer
  describe a "build only when someone asks" rule** that stopped applying in August. Which templates get built is the maintainer's
  choice, and those pages now say so.

## Fixed

- **Two worked examples disagreed about one performance figure.** The RAID log example called it a staging
  measurement and the KPI dashboard example a production one; they now agree.
- **The library's status page listed 27 of its 31 bundles by family**, leaving out four; it now lists all
  of them.
- **The security page said this repository runs no server.** An MCP server has shipped since `v0.6.0`. The
  page now describes it: it runs locally, opens no network port, and one of its five tools writes a file,
  which is worth knowing before you give the server to an agent.
- **Seven sentences in four bundles still called sibling bundles "forthcoming"**, months after those
  siblings shipped. They now name them as siblings, and the release checklist's search catches the word.

## Known issues

- **Nothing here makes any bundle better.** All 33 are `beta`, and no page calls one proven.
- **The definition of ready is admitted on practitioner and pattern sources only.** Neither the Scrum Guide
  nor SAFe's glossary names it, and the bundle says so plainly.
- **Build cost is measured, not a rate.** Each new bundle's report is in `bundle-builds/`: the issue log
  cost $16.76 at API list rates and the definition of ready $13.89. Three builds through the same workflow
  is still too few to call typical.
