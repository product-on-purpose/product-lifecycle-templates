# How the site works

The library publishes a website at
<https://product-on-purpose.github.io/product-lifecycle-templates/>. It renders every bundle for a
human reader, and **nothing about it is hand-listed**: every page comes from the same files the
gate already checks.

This page explains the machinery and the three decisions inside it that are easy to get wrong.
It is understanding-oriented. To run the site locally, read
[`scripts/README.md`](../../scripts/README.md) and `site/package.json`. To know what the site is
*for*, read [ADR 0046](../internal/decisions/0046-the-site-is-astro-starlight-under-pattern-s.md)
and [ADR 0052](../internal/decisions/0052-the-site-is-a-standalone-property-at-the-github-io-path.md).

## The shape

One workflow, [`site.yml`](../../.github/workflows/site.yml), with two jobs.

```
push to main / pull_request / workflow_dispatch
  |
  +-- job: build            (runs for BOTH pushes and pull requests)
  |     checkout  fetch-depth: 0
  |     setup-node  version from .nvmrc
  |     npm ci  in site/, from the committed lockfile
  |     npm run build
  |       |-- prebuild -> npm run gen -> scripts/gen-site.mjs
  |       +-- astro build -> site/dist
  |     GUARD  no page claims a bundle is proven   (scans the GENERATED MDX, not dist)
  |     GUARD  every internal link resolves in a browser
  |     GUARD  no published route disappeared
  |     GUARD  a favicon resolves on every page, 404 included
  |     GUARD  every edit link points at a tracked file
  |     upload-pages-artifact   <- reached only if all five exited 0
  |
  +-- job: deploy           needs: build, AND push to main only
        deploy-pages

concurrency: group pages, cancel-in-progress false
  -> two rapid pushes to main queue and both finish; neither cancels the other
```

A pull request gets the **identical** build and the **identical** guards, and deploys nothing. That
is why there is no separate "validate" workflow: a second recipe is a second thing to drift.

## Generation: four inputs, one output directory

[`scripts/gen-site.mjs`](../../scripts/gen-site.mjs) is dependency-free Node ESM. It reads four
inputs. Two are generated whole by the Python tooling and a third has its derived flags gated by it,
which is why the generator needs no YAML parser:

| Input | Generated by |
|---|---|
| `manifest.json` | `tools/gen-manifest.py` |
| `sections.json` | `tools/gen-sections.py` |
| `atlas/catalog-data.json` | hand-maintained research catalog; its `built` and `state` flags are derived and gate-checked by `tools/gen-atlas.py` |
| `templates/<id>/*.md` | the bundle itself, read verbatim |

It writes into exactly one place, `site/src/content/docs/bundles/`, which is gitignored and rebuilt
on every build. Hand-authored narrative pages live elsewhere under `site/src/content/docs/`, both at its top level
and in a `families/` subdirectory, and the generator never touches them. Its own header states the rule more sharply than a policy would: *this script does not know
they exist and must not learn.*

**The consequence worth holding onto:** adding a bundle to `templates/` and regenerating
`manifest.json` publishes a page. Nobody edits the site to do it. The regeneration is not a separate
thing to remember either: the generator reads `manifest.json` rather than scanning `templates/`, and
`gen-manifest.py --check` is a required CI step, so a bundle that never reached the manifest fails
the content gate long before anyone looks at the site.

## The three decisions that are easy to get wrong

### 1. The guards run against the artifact that ships

Every guard runs **inside the build job, between `astro build` and `upload-pages-artifact`**. Four of
the five run against `./site/dist`, the exact directory the next step uploads. **The honesty guard is
the exception**: it re-runs the generator in `--check` mode and scans the generated MDX in
`site/src/content/docs/bundles/`, one step upstream of the built HTML. It catches the same prose
either way, but it is worth knowing it is checking the source of the page rather than the page.

The obvious alternative is to guard in one workflow and deploy in another. The reference
implementation this site was ported from does exactly that, and the two workflows race: a guard
failure does not stop a deploy, because **the artifact that is checked is not the artifact that
ships**. Copying that structure would have inherited the gap.

Each guard has also been run against a deliberately broken fixture and **observed to fail**. That
discipline comes from a real defect, recorded as DF-7: a CI self-test degraded to a skip and printed
OK, so CI had never verified the thing it claimed to. The rule that came out of it is short.
**A guard that has never gone red is a report, not a gate.**

### 2. The build command is `npm run build`, not the all-in-one action

`withastro/action` would be the conventional choice and is deliberately not used. **The reason this
repository recorded for that, until 2026-09-22, was wrong**, and the correction is worth leaving
visible rather than quietly swapping. The workflow comment said the action "runs astro build directly
with no pre-build hook and would skip the generator entirely". It does not: its build step is
`run: ${{ inputs.build-cmd || '$PACKAGE_MANAGER run build' }}`, so by default it runs
`npm run build`, which fires `prebuild` and therefore the generator, exactly as this workflow does.
Verified against the action's own `action.yml` on 2026-09-22.

**The real reason is structural, and it is the one the guards exist for.** That action bundles
`actions/upload-pages-artifact` into itself. Using it would leave **no seam between `astro build` and
the upload**, which is precisely where every guard has to run for the artifact that is checked to be
the artifact that ships. The decision was right; the reason recorded for it was not.

### 3. The base path is one literal

[`scripts/site-base.mjs`](../../scripts/site-base.mjs) exports `BASE`, and `astro.config.mjs`, the
generator and the link checker all import it. A base that disagrees between the build and a validator
passes every local check and then 404s on the live site.

An earlier draft kept a second copy in the generator plus a startup assertion that the two matched.
That assertion is gone, and the reason is worth generalising: **one literal cannot disagree with
itself.** The same pattern governs the Node version (`.nvmrc`, never a literal in the workflow) and
the dependency set (`npm ci` against a committed lockfile, never `npm install`).

## What each guard actually catches

| Guard | The failure it exists for |
|---|---|
| **Honesty** | A page calling a bundle proven, verified or validated. See below. |
| **Rendered links** | A link that is filesystem-correct and still 404s, because pages build to `slug/index.html` and are served one URL level deeper than their source. |
| **Route parity** | A removed or renamed URL, which is a "Site not found" for every existing link and bookmark. |
| **Favicon** | A page with no resolvable icon, `404.html` included, since that is the page a stale external link lands on. |
| **Edit links** | An "Edit this page" link pointing at a path that is not git-tracked. |

Two are subtler than they look.

**Edit links asserts the target is tracked, not merely present.** A page that loses its `editUrl`
stamp falls back to the generated, gitignored content path, which exists on disk in CI exactly as it
does locally. An existence check passes while the link 404s on GitHub.

The workflow checks out with `fetch-depth: 0`, but **not because this guard requires it**:
`git ls-files` reads the index, which a shallow clone has. The workflow's own comment keeps the full
history in case a future guard needs it. The two are related by intent, not by necessity.

**Route parity is asymmetric, on purpose.** A route that *disappeared* fails the build. A route that
was *added* is allowed and merely reported, with a note to refresh the baseline when convenient. So
landing a new bundle cannot fail **this** guard, while deleting one cannot quietly break every
inbound link. The other four still apply to the new page: a broken internal link, a missing edit-link
target, or a sentence calling the bundle proven will each fail the build. Refresh the baseline with `node scripts/check-route-parity.mjs --update` and commit it with a
reason.

## The honesty gate, and why it is not a word filter

The rule is that **no page may call a bundle proven**
([ADR 0055](../internal/decisions/0055-retire-the-zero-fills-disclosure.md) kept this when it retired
the fill-count disclosure). It is enforced by `gen-site.mjs --check` against the generated pages,
because the gate is on what ships.

`gen-site.mjs`'s own comment records that a naive implementation scanning for `proven`, `verified`
and `validated` flagged **79 honest sentences** (that comment is the only record of the number): a
bug-report example where a fictional tester signs off a fictional fix, a test-plan guide using
"verified" for its ordinary meaning. Failing those teaches whoever hits them to weaken
the rule for everyone, which is how an honesty gate dies.

So a hit has to clear three conditions:

1. **Not negated**, checked in the part of the sentence *before* the matched word, because this
   repository hard-wraps its prose and a line scanner would split "not yet proven" across two lines.
2. **About *this page's own* bundle** - its id or its title, or an explicit self-referential phrase -
   rather than any bundle the page happens to name. On the index page, which has no single bundle,
   only the self-referential phrases can match.
3. **Stricter inside a fenced block.** Unfenced, the library is speaking, so its own id or title
   counts as self-reference. Inside a fence the bundle's title is just the document's subject, so
   only an explicit meta-phrase counts: "this bundle", "this template", "this library" or
   "these templates".

Fencing is therefore not an escape hatch: *"This template is proven to cut review time by 40%"*
planted in a template body still fails, on both the word and the percentage. The deliberate escape is an `<!-- honesty-ok: ... -->` comment **on the same physical line as the
flagged word or percentage** - not the same sentence or paragraph, which matters because this
repository hard-wraps. It is visible in the diff and has to be justified.

**If you are authoring a bundle, this is the one site mechanism that can fail your build**, and it
fails the site build rather than the content gate. Writing about the document type is safe; writing
that *this bundle* has been proven is not.

## What the site is not

- **Not an acquisition path.** It serves no machine-readable artifact. An agent wants the tree or the
  MCP server; `AGENTS.md` says so directly.
- **Not a required check, as far as this repository can tell you.** `site.yml` is separate from
  `ci.yml` by design, so a site failure cannot block a template change - that half is structural and
  checkable. That the content gate is the *only* required check is a **GitHub branch-protection
  setting**, which lives in repository settings and not in the tree. `site.yml` and
  `.github/workflows/README.md` both assert it, and `site.yml` hedges its own assertion with "until
  the site has proven itself". Treat it as current policy, not as something this page can prove.
- **Not a place build-cost reports appear.** `bundle-builds/` is not among the generator's inputs.
  Those reports are internal provenance, not a reading surface.
- **Not proof of anything.** The site renders what the library has; it does not make any of it more
  true. Every bundle on it is `beta`.
