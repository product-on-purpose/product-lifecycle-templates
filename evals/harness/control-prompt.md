# The control-arm prompt

**Version 1, 2026-08-08.**

This file is public and versioned for one reason: **the easiest way to fake a good efficacy number is a
weak control.** A thin prompt ("write a PRD") measures prompt effort rather than template value, and any
skeptic can halve the published gap by re-running with a decent one. So the counterfactual is written here,
in the open, and a reader who thinks it is unfair can say exactly which sentence is unfair.

The design rule that governs edits to this file: **if making the control stronger erases the gap, that is a
finding about the templates**, and it is better to discover it here than to have someone else demonstrate
it after publication.

## What the control gets and does not get

**Gets:** the scenario, the context pack, the document type by name, and the generic instruction below,
which names the standard advice a competent practitioner would already follow.

**Does not get:** this library's templates, guides, companions, section names, ordering, or vocabulary. If
any of that leaks in, the arms are no longer independent and the run is void.

**Length parity.** The instruction below is written at roughly the length of the treatment arm's
instruction, so the gap cannot be an artifact of one arm simply being told more.

---

## The prompt

> You are an experienced practitioner writing a **{doc_type}** for the situation described below. Write
> the document you would actually hand to the team.
>
> Bring the standard discipline this kind of document deserves:
>
> - **State the problem with evidence**, not as an assertion. Say what you know, how you know it, and how
>   confident you are.
> - **Define success up front**, in terms someone could later check. If a number matters, name it and say
>   what value would count as good.
> - **Say what is out of scope**, explicitly, so a reader can tell an omission from a decision.
> - **Name the risks and the unknowns**, including the ones that would be uncomfortable to raise, and say
>   what you would do about each.
> - **Make it actionable.** A reader should be able to act on this without booking a meeting to ask you
>   what you meant.
> - **Distinguish what you were told from what you concluded.** Where the input is thin or contradictory,
>   say so plainly rather than smoothing it over.
> - **Be concrete.** Prefer a specific claim you can defend over a general one that sounds safe.
>
> Structure it however you judge best for this document type and this audience. Write the whole document,
> not an outline.

## Change log

A change here changes the counterfactual, which changes every number ever compared against it. So each
version is dated and kept, and results record which control version produced them.
