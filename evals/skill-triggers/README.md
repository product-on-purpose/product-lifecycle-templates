# Skill-trigger suite

**This suite measures whether an agent loads the right skill for a request.** It is not part of the efficacy
eval in the folder above, which measures whether a template makes a document better. An agent decides whether to
load `plt-fill-template` or `plt-grade-doc` by reading each skill's description, so the description is the trigger.
This suite sends 53 short requests to a fresh agent and checks which skill it loads.

Run it at any release that changes a skill description. Both descriptions are generated by
[`tools/gen-skill-descriptions.py`](../../tools/gen-skill-descriptions.py), so the changes that need a run are a new
bundle, a changed `trigger_name`, and a change to that script's order table or sentences.
[ADR 0093 (generated skill descriptions, split by family group)](../../docs/internal/decisions/0093-skill-triggers-split-by-family-group-and-generated-from-the-manifest.md)
records why.

## How to run it

```
python evals/skill-triggers/run.py               # print the plan and its cost caps; spends nothing
python evals/skill-triggers/run.py --go          # the release procedure, about USD 12 to 14
python evals/skill-triggers/run.py --smoke --go  # one request, one run, about USD 0.05
```

The release procedure runs three evals at once, all on Sonnet:

| Eval | Wording | Cases | Runs each |
|---|---|---|---|
| `suite-new` | the working tree | all 53 | 5 |
| `fragile-new` | the working tree | the 2 tagged `fragile` | 15 |
| `fragile-base` | the latest release tag, or `--base <ref>` | the 2 tagged `fragile` | 15 |

Then [`score.py`](score.py) applies the release rule:

- **A fragile case blocks the release** when the new wording loads the right skill on 3 or more fewer runs in 15
  than the old wording did in the same session. The maintainer reads the result before the release goes ahead.
- **Any other case is compared with [`baseline.json`](baseline.json).** A drop of 2 or more runs in 5 prints a
  `READ` line. It does not block, because one 5-run result is noisy.

Results, logs and per-run traces land in the system temp folder, or in `--out`, which must be outside the repository.
Nothing a run writes is committed. Record the result in the release note instead.

## Why the rule has two parts

**Five runs cannot separate a regression from noise on the fragile cases.** At five runs, round 4 of the 2026-11-26
tests flagged the spike report, which was noise. It also passed the data dictionary, which was a real regression,
found only at 15 runs. And the data-dictionary rate swings between sessions, from 4 to 14 of 15 under identical
wording. So a fragile case runs on both wordings in one session, never against a stored number. Replayed on the
round-5 files, the rule blocks that data-dictionary regression, 14 of 15 down to 8, and passes the spike report.

## The files

| File | What it is |
|---|---|
| [`cases.json`](cases.json) | The 53 requests: 27 ask to write a document, 22 ask for a grade, and 4 must load no skill. Each has an `expect` of `fill`, `grade` or `none`, and tags |
| [`build-arm.py`](build-arm.py) | Builds a test copy of the plugin from the working tree or a git ref, with one eval case per request |
| [`run.py`](run.py) | Runs the release procedure, or the smoke test |
| [`score.py`](score.py) | Prints each case's pass count and the skills each run loaded, and applies the rule |
| [`baseline.json`](baseline.json) | The v0.28.1 wording's pass counts on all 53 cases, 278 of 285 runs, from the trial runs |

## What a pass does and does not show

- **It shows which skill loaded, not whether the document came out well.** The grader checks the first three turns
  for a skill call. The test copy of the plugin has no templates, so a loaded fill skill finds nothing to fill.
- **The test is kinder than a real session.** Only this plugin is loaded, so no other skill competes for the
  request. A user with many plugins installed may see lower rates.
- **One model.** Every run uses Sonnet. Opus and Haiku were never tested.
- **Two known misses are not wording defects.** `g3-status-report` loads no skill under any wording, because the
  agent answers the request directly. The fragile pair misses when the agent searches the empty test folder for
  the schema or the notes and declines to invent them.
- **Graders match a skill-name prefix**, `plt-fill-` or `plt-grade-`, so a split that adds skills of either kind
  needs no grader change. A split into skills that each fill and grade would need new graders.

The cases were written for the 2026-11-25 trial and grew over six rounds, weighted toward rare types and toward names
that were shortened. 32 of the 59 types have no write-a-document request of their own.
